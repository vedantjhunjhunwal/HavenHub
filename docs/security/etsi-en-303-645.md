# ETSI EN 303 645 (consumer IoT cyber security) – control mapping

ETSI EN 303 645 is the European baseline for consumer IoT security. It underpins the UK PSTI regime
and the EU Radio Equipment Directive delegated act. This table maps each of its 13 provision groups
to what HavenHub's cloud service does and the tests that check it. Provisions that only a physical
device can meet (hardware, firmware signing) are marked as device-side.

| Provision | What HavenHub does | Evidence |
|---|---|---|
| 5.1 No universal default passwords | No shared credentials. Each device gets a unique random 256-bit secret when it redeems a single-use pairing code that expires after 10 minutes. User passwords need 12+ characters and are checked against a blocklist; panel PINs refuse weak values (1234, 0000...). | REQ-01, REQ-05, REQ-14; `DeviceAndCommandTests.Pairing_codes_work_once_and_each_device_gets_its_own_secret` |
| 5.2 Manage reports of vulnerabilities | `SECURITY.md` publishes a disclosure policy, contact and response times. | `SECURITY.md` |
| 5.3 Keep software updated | Devices report their firmware version. Anything below `MinimumFirmware` is refused at pairing (HTTP 426) and at connection (`firmware_update_required`). | REQ-08; `Outdated_firmware_is_refused_at_pairing_and_at_connection` |
| 5.4 Securely store sensitive security parameters | Device secrets are encrypted with AES-256-GCM, bound to the serial, under a master key held outside the database. Passwords and PINs are PBKDF2-HMAC-SHA256 hashes. Pairing codes are stored only as SHA-256 digests. The service refuses to start outside Development without configured keys. | REQ-06; `Device_secrets_are_never_stored_in_plain_text` |
| 5.5 Communicate securely | TLS for transport (HSTS in production) plus HMAC-SHA256 on every device message in both directions, with freshness (60 s skew), ordering and nonce replay checks. Constant-time comparisons throughout. | REQ-07; `Replayed_tampered_and_stale_reports_are_dropped`, `Devices_with_the_wrong_secret_cannot_connect` |
| 5.6 Minimise exposed attack surfaces | Zero third-party packages (ADR-0001). Request bodies capped at 64 KB, device frames at 16 KB. No server banner. Non-members get 404, not 403. Least-privilege roles (a guest cannot unlock). | REQ-04, REQ-22; ADR-0001 |
| 5.7 Ensure software integrity | Device-side (secure boot). Cloud side: build with warnings-as-errors and security analyzers, CodeQL on every push, and a hash-chained audit log that exposes tampering with security records. | REQ-19; `.github/workflows` |
| 5.8 Ensure that personal data is secure | Personal data (email, home name, activity) is only reachable by home members; tokens never appear in URLs; `Cache-Control: no-store` on all API responses. | REQ-03, REQ-04, REQ-22 |
| 5.9 Make systems resilient to outages | Comfort commands queue while a device is offline; heartbeat monitoring marks silent devices offline; housekeeping survives a failed pass; devices reconnect and receive queued commands. Alarm timers are persisted, so a restart does not lose an entry delay. | REQ-10, REQ-12, REQ-23 |
| 5.10 Examine system telemetry data | Device online/offline, low battery, tamper and jam events are recorded and reported; the reliability report shows per-device acknowledgement rates. | REQ-15, REQ-17 |
| 5.11 Make it easy for users to delete user data | `DELETE /api/homes/{id}` and `DELETE /api/me` (with password confirmation) remove devices, commands and events, and disconnect devices at once. | REQ-20 |
| 5.12 Make installation and maintenance easy | Pairing is one code typed into the device app; the dashboard shows device health, battery and firmware. | Dashboard |
| 5.13 Validate input data | Every endpoint validates types and ranges; device commands are validated per device type with safety interlocks; all SQL is parameterised; serials are pattern-checked with a regex timeout. | REQ-09, REQ-24 |

## OWASP coverage at a glance

| OWASP item | Control |
|---|---|
| A01 Broken access control / API1 BOLA | Every home route checks membership and role; cross-home device ids return 404 (`Non_members_get_404_for_everything_in_someone_elses_home`). |
| A02 Cryptographic failures | PBKDF2 600k, AES-GCM, HMAC-SHA256, CSPRNG only; analyzers ban weak algorithms (CA5350/CA5351). |
| A03 Injection | Bound parameters only (CA2100 enforced), dashboard writes with `textContent` only. |
| A04 Insecure design | Threat model (`threat-model.md`), safety interlocks, fail-fast for security commands. |
| A05 Security misconfiguration | Secure headers, no banner, keys required outside Development. |
| A07 Identification and authentication failures | Lockout, uniform failure responses, revocable tokens, rate limits. |
| A09 Logging and monitoring failures | Hash-chained audit log of logins, failures, arming, unlocks, pairing and deletions. |
| API4 Unrestricted resource consumption | Separate rate-limit buckets for auth, pairing, PIN and commands; body and frame size limits; bounded SSE queues. |
